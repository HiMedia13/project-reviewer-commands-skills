# v0.4.0 — Per-repo isolation, manifest-based frontend exclusion, deepened tech-stack evidence

Date: 2026-05-18
Status: Approved (brainstorming)

## Problem

Three issues observed running the plugin against real repos:

1. **Result collision.** `<workdir>` (default `.reviewer`) is flat and repo-agnostic.
   Evaluating multiple GitHub repos from the same directory overwrites
   `last-review.json` / `scope.json`, mixes reports in one `output/`, and—worst—
   the single shared `.repocache/` clone collides (clone fails or
   `fetch+hard-reset` corrupts the other repo). Incremental scope also compares a
   new repo against the previous repo's commit SHA, producing nonsense scope.

2. **Frontend leaks into evaluation.** The frontend-exclusion rule keys off a
   hardcoded directory-name list (`frontend/client/web/ui/static`) plus a fixed
   extension set. Frontends laid out differently slip through and get evaluated
   by default, which the user does not want. Default should be **backend + AI
   only**; frontend only with an explicit opt-in flag.

3. **Shallow tech judgment.** Stack rows report "library X is used" rather than
   whether each technology's core configuration is correct (e.g. LangChain tool
   definitions, APScheduler triggers/timezone, ML model data/eval-metric
   validity). The user wants per-technology deep configuration assessment.

## Goals

- Isolate every run's state per target so concurrent/serial multi-repo use never
  collides, while keeping the "latest run only, no cumulative DB" principle.
- Make the default scope genuinely backend + AI; exclude frontend robustly via
  manifest signals, not directory names; keep `--with-frontend` opt-in.
- Deepen `review-techstack` evidence to per-technology configuration correctness,
  with no JSON schema changes, staying within the v0.3.0 strictness rules.

## Non-goals (YAGNI)

- No automatic migration of an existing flat `.reviewer` layout.
- No cumulative/keyed result database.
- No new `deep_checks` schema field, no new report column.

## Design

### A. Per-target isolation

**Slug derivation (deterministic, in P0, zero LLM):**

- Normalize the target string: strip surrounding quotes/whitespace, strip a
  trailing `/`, strip a trailing `.git`, strip `protocol://` and any
  `user[:pass]@` credentials, lowercase the host.
- Git URL (`https://github.com/Owner/Repo.git`, `git@github.com:Owner/Repo.git`,
  `ssh://…`): build `host_owner_repo` → e.g. `github.com_Owner_Repo`.
- Local path: `local_<basename>` where basename is the final path segment.
- Suffix: first 6 lowercase hex of `sha256(normalized full target string)`.
- Final slug = `<sanitized>_<hash6>`, where sanitize replaces any character
  outside `[A-Za-z0-9._-]` with `-` and collapses runs of `-`.
- The full-target hash guarantees two distinct sources never share a folder even
  when `host_owner_repo` / basename coincide.

**Folder layout:**

```
<workdir>/
  <slug>/
    last-review.json
    scope.json
    output/report-<timestamp>.html
    .repocache/          # this repo's clone; absent for a local-path target
```

For a git-URL target the clone goes to `<workdir>/<slug>/.repocache/`. For a
local-path target the path is used in place (no `.repocache/`), unchanged from
today. All P4 outputs and `scope.json` are written under `<workdir>/<slug>/`.

**Scope correctness:** incremental reads `<workdir>/<slug>/last-review.json`,
which by construction belongs to the same target, so the prior-SHA diff is
always same-repo. Defense-in-depth retained: if the stored `repo` field does not
match the resolved target, fall back to `full`.

**`/review-project` and `/review-scope`:** compute the slug in P0 and route every
path through `<workdir>/<slug>/…`. `/review-scope` additionally prints the
resolved slug and the per-repo workdir path so the preview matches a real run.

**`/review-report`:** gains an optional first positional `[target]`
(argument-hint `/review-report [target] [--workdir DIR]`).

- If `target` given: derive the slug, read `<workdir>/<slug>/last-review.json`.
- If omitted: scan `<workdir>/*/last-review.json`, pick the most recently
  modified, and print which repo (its stored `repo` field + slug) was chosen.
- Legacy fallback: if no `<workdir>/*/last-review.json` subdir files exist but a
  legacy flat `<workdir>/last-review.json` does, use it and note it is legacy.
- If nothing is found, the existing clear "run `/review-project` first" error.

### B. Manifest-based frontend exclusion (default = backend + AI only)

Applied in P0, BEFORE scope/cache (so the incremental diff matches what is
actually evaluated), replacing the directory-name-keyed rule.

**Primary detection — manifest signals.** A directory is a *frontend root* if it
contains a `package.json` whose dependencies/devDependencies include a frontend
framework (`react`, `react-dom`, `vue`, `@vue/*`, `next`, `nuxt`, `svelte`,
`@sveltejs/*`, `@angular/core`, `solid-js`, `preact`) **or** the directory
contains a frontend bundler/framework config (`vite.config.*`, `next.config.*`,
`nuxt.config.*`, `svelte.config.*`, `angular.json`, or a `webpack.config.*` with
a browser/frontend entry).

The frontend source governed by that manifest = files at or under the frontend
root with extensions `.js .jsx .ts .tsx .vue .svelte .mjs .cjs` plus the
always-UI extensions `.css .scss .less .html`. These are excluded by default.

**Secondary fallback.** Keep the prior extension/directory heuristic for
frontends that ship no manifest, so they are still excluded by default.

**Always included regardless of location:** backend / AI languages
`.py .go .rs .java .rb .php .cs .kt .scala .ipynb` (and similar backend
extensions). The AI part is explicitly never excluded.

**Opt-in:** `--with-frontend` includes the frontend source in scope.

`/review-scope` prints detected frontend roots, the signal that triggered each
(which dependency / config file), and the excluded-file count.

### C. Deepened tech-stack evidence (no schema change)

`review-techstack` must evaluate each major detected technology's
**core configuration correctness**, not mere presence. It applies a
non-exhaustive per-technology pattern when the technology is present:

- **LLM / agent orchestration** (LangChain, LlamaIndex, …): are tools / chains /
  agents defined with proper schemas, are prompts and output parsers wired, is
  there error handling around model calls.
- **Schedulers** (APScheduler, Celery beat, cron-like): job/trigger definitions,
  timezone, misfire/coalesce policy, jobstore persistence.
- **ML / AI models**: training-data provenance, evaluation metrics and their
  meaning, train/serve separation, reproducibility/versioning — **only when the
  repo documents it in code/docs**; if absent, state "근거 없음" and neither
  fabricate nor over-penalize beyond "undocumented".
- **Web frameworks / ORMs / messaging / etc.**: equivalent configuration depth.

Concrete configuration evidence (file:line, setting values) goes in `evidence`;
the deep judgment in `rationale`; `used_well` / `stack_score` must reflect it.
"Declared only, no deep evidence" must not score `good`.

`review-evaluator` verifies these deep claims, web-searching a technology's
intended configuration when unknown, and downgrades shallow `good` ratings that
lack deep evidence — consistent with the existing v0.3.0 strictness rules
(verified high-severity → stack_score < 50; accumulated serious issues →
stack_score < 80). No JSON fields are added; the existing `tech_assessment`
schema is unchanged. `rubric.md` and `SKILL.md` gain a short "depth requirement"
note only.

## Manual verification

1. Two different git URLs from the same cwd → two distinct `<workdir>/<slug>/`
   trees; neither `last-review.json` nor `.repocache/` collides; second run's
   scope is not `incremental`-against-the-other-repo.
2. Re-running the *same* URL → same slug, incremental works against its own
   prior SHA.
3. A repo with a React/Vue/Next frontend in a non-`frontend/` directory →
   default run excludes that frontend (scope preview shows the manifest signal);
   `--with-frontend` includes it; `.py` AI files always included.
4. `/review-report` with no arg after several repos → picks the newest and names
   the repo; with `[target]` → renders that repo; legacy flat file still works.
5. A repo using LangChain/APScheduler/an ML model → stack rows cite concrete
   config evidence (file:line, settings) and `used_well` reflects deep
   correctness, not mere presence; undocumented model aspects say "근거 없음".
