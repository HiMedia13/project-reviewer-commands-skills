# v0.5.0 — Clickable architecture diagram + per-component scoring

Date: 2026-05-18
Status: Approved (brainstorming)

## Problem

The HTML report leads with the tech-stack-fit assessment and per-file findings
but gives no view of how the project is *structured*. A reviewer cannot see the
component layout, how each part is internally composed, why it is shaped that
way, or how good each part is. The user wants the report to also draw the
architecture and let the reader click any part to see its internals, the
inferred rationale, and an LLM score.

## Goals

- A new subagent reads the whole (in-scope) codebase and infers a
  component-level architecture: components, their internal composition,
  dependency edges, a per-component rationale and score, and an overall score.
- The self-contained HTML report renders that as a clickable diagram: each
  component is a box; clicking it reveals internal composition, rationale, and
  score. No external requests, no XSS.
- Architecture is a third, independent scoring axis — never blended into the
  tech-stack or code-quality scores.
- `/review-report` re-renders the diagram from stored data with zero LLM cost.

## Non-goals (YAGNI)

- No general graph-layout engine (deterministic layered layout only).
- No pan/zoom, no diagram editing.
- No file-level drill-down (component granularity only).
- No frontend internals unless `--with-frontend` (frontend otherwise appears as
  a single non-scored boundary node).
- No new evaluator/scoring JSON fields beyond the `architecture` object.

## Design

### A. New subagent `review-architecture`

- File `agents/review-architecture.md`. `model: sonnet`,
  `tools: Read, Glob, Grep`. Project-level (whole-codebase), like
  `review-techstack`. Does NOT evaluate build/run/test. Ignores injected
  `<system-reminder>` text. Korean free-text; English JSON keys/enums (the
  existing localization rule).
- Runs in **P2**, dispatched in the SAME single message as the existing four
  criteria agents (now five parallel agents: `review-library`, `review-eng`,
  `review-deadcode`, `review-techstack`, `review-architecture`). It receives the
  in-scope file list + the scanner map.
- It infers logical components (layers / modules / services — e.g. API layer,
  scheduler, LLM orchestration, data layer, model training), their internal
  composition, dependency edges, a rationale, and scores.
- Frontend that was excluded by the v0.4.0 scope rule appears as a single
  `boundary: true` context node (no internals, no score) so the diagram is not
  misleading; backend/AI components are fully assessed.

Output — exactly one JSON object:

```json
{
  "summary": "한국어 전체 아키텍처 서술",
  "arch_score": 0,
  "components": [
    {
      "id": "api",
      "name": "API 계층",
      "files": ["app/api/...", "..."],
      "internal": "내부가 어떻게 구성되어 있는지 (한국어)",
      "rationale": "왜 이렇게 구성한 것으로 보이는지 (한국어)",
      "score": 0,
      "boundary": false
    }
  ],
  "edges": [ { "from": "api", "to": "db", "label": "한국어 관계(선택)" } ]
}
```

- `id` is a short literal ASCII slug, unique within `components`, referenced by
  `edges.from`/`edges.to` and used as the click target. Stays literal (not
  localized).
- `arch_score` and `score` are integers **0–100, higher = better**, same anchors
  as `rubric.md` (90–100 exemplary … 0–39 serious; a verified high-severity-
  equivalent structural problem forces a score below 50).
- A `boundary: true` component has `score: null`, `internal: null`,
  `rationale: null`; it is context only and is excluded from the `arch_score`
  computation. An empty `components` array is valid.

### B. Evaluator (P3) verifies the architecture

`review-evaluator` additionally receives the `architecture` object and verifies
it the same way it verifies `tech_assessment`:

- Drop hallucinated components/edges with no code basis.
- Challenge unsupported high `score`/`arch_score`; downgrade declared-only or
  evidence-thin component judgments (consistent with the existing depth rule).
- WebSearch an unfamiliar architectural pattern's intended shape before ruling.
- Rewrite `summary` so it does not contradict the verified findings.

No JSON schema fields are added; the evaluator returns the verified
`architecture` alongside `findings` and `tech_assessment`. Never-raise: a
malformed/absent architecture from either agent degrades to "no diagram" and
the run continues.

### C. Scoring — independent third axis

`rubric.md` and `SKILL.md` gain an **Architecture axis**, independent of the
existing two:

- Primary headline: verified `stack_score` (unchanged).
- Secondary: code-quality mean of `library`/`eng`/`deadcode` (unchanged).
- **Architecture (independent):** the verified `arch_score` is the headline for
  this axis, reported on its own; per-component `score`s are listed. `arch_score`
  is the agent's holistic architecture judgment (as `stack_score` is for
  tech-stack) — verified/adjusted by the evaluator, NOT a mechanical mean of
  component `score`s; `boundary` components carry no score and are excluded from
  the agent's `arch_score` reasoning and from any displayed component-score
  aggregate. The architecture axis is NEVER averaged into the tech-stack or
  code-quality scores, and they are never averaged into it. Only verified data
  contributes; if no verified `arch_score` exists the headline shows `N/A`.
  Same 0–100 anchors as the rubric.

### D. Report template — self-contained diagram + click detail

`skills/review-methodology/report-template.html` gains an "아키텍처" section.

- The verified architecture is embedded as
  `<script type="application/json" id="arch-data">…</script>`. Vanilla JS
  reads it with `JSON.parse(document.getElementById('arch-data').textContent)`.
  No external requests, no library.
- All LLM-produced strings are rendered into the DOM via `textContent` / DOM
  node creation — never `innerHTML` — so embedded markup cannot execute. When
  serializing the JSON blob, `<` is escaped (e.g. `<` → `<`) so a
  `</script>` in any field cannot break out of the script element.
- Layout: components are boxes in a deterministic layered layout (column =
  dependency depth derived from `edges`; stable ordering by `id`). Dependency
  cycles are broken deterministically — when computing depth, a back-edge to an
  already-visited component is ignored for depth purposes but the edge is still
  drawn. Edges are inline SVG arrows between boxes. This is intentionally simple
  and robust, not a general graph engine.
- Each box shows `name` and a score badge colored by the rubric band
  (90–100 / 70–89 / 40–69 / 0–39). `boundary` nodes render dashed/grey, labeled
  "평가 제외", with no badge.
- Clicking a box opens a detail panel showing `internal`, `rationale`, and the
  `score` + band. Boxes are `<button>` elements (keyboard accessible);
  clicking again or a close control dismisses the panel.
- New template tokens: `{{ARCH_SUMMARY}}`, `{{ARCH_SCORE}}`,
  `{{ARCH_DATA_JSON}}`. The existing 11 tokens are unchanged → 14 total. Token
  substitution still HTML-escapes text tokens; `{{ARCH_DATA_JSON}}` is a
  JSON-serialized, `<`-escaped blob.
- Empty/absent architecture → the section renders a "아키텍처 정보 없음"
  placeholder and emits no script.

### E. Orchestrator, persistence, re-render

- `commands/review-project.md`: P2 dispatches the five agents in one message;
  P3 passes the `architecture` object to the evaluator; P4 scores the
  architecture axis (verified `arch_score` headline + per-component, boundary
  excluded), HTML-escapes, fills the three `{{ARCH_*}}` tokens, and persists
  `architecture` into `<workdir>/<slug>/last-review.json` (English keys). The
  Korean terminal summary gains a third line: architecture score + one-line
  summary, explicitly a separate axis (never combined).
- `commands/review-report.md`: re-renders the architecture section and diagram
  from the stored `architecture` with zero LLM calls; `last-review.json`
  schema gains the `architecture` object.
- `skills/review-methodology/SKILL.md`: add `review-architecture` to the P2
  list; add the Architecture axis to Scoring; extend the never-raise note and
  the Localization rule (architecture free-text Korean; keys/enums and
  component `id` literal).
- `.claude-plugin/plugin.json` + `marketplace.json`: version `0.5.0`;
  description notes the clickable architecture diagram (byte-identical strings).
- `README.md`: v0.5.0 note; Outputs/How-it-works mention the architecture axis
  and diagram; Manual-verification adds a diagram check.

## Manual verification

1. `/review-project <repo>` on a multi-component backend → report has an
   "아키텍처" section; boxes match real modules; edges reflect real
   dependencies; clicking a box shows internal/rationale/score.
2. The HTML opens with no external requests; a component whose text contains
   `</script>` or `<img onerror=...>` renders as literal text (no execution).
3. A repo with an excluded frontend → exactly one dashed "평가 제외" boundary
   node, no score on it, `arch_score` computed from backend/AI only.
4. Terminal summary shows three independent axes; `arch_score` is never blended
   into stack or code-quality.
5. `/review-report` (no new run) re-renders the same diagram, zero LLM calls.
6. A subagent returning malformed architecture JSON → report shows
   "아키텍처 정보 없음", the rest of the report still renders, no abort.
